Executive conclusion

I reviewed the full Wolters Kluwer licensing Q&A transcript and validated the relevant Genesys Cloud capabilities against current official documentation. The transcript is the source of truth for WK's stated business requirements and priorities.

There is an important distinction that changes the recommendation:

WK does not necessarily need Speech and Text Analytics to achieve PCI DSS compliance.

Genesys explicitly states that Automated Sensitive Data Masking/Redaction is not itself PCI DSS compliant. It is a secondary safety measure. Genesys identifies Secure Pause and Secure Call Flows as the features externally validated by a QSA as PCI DSS Level 1 compliant.

Source: Genesys Cloud Resource Center

That means the lowest-cost path for the requirement Manjeet repeatedly articulated—“make every North America agent PCI compliant”—may be to use the PCI controls WK already has rather than license STA across the remaining population.

What WK actually asked us to solve

The transcript establishes these requirements:

  • Approximately 2,149 North America users are the target population.
  • Approximately 1,080 already have WEM, leaving about 1,069 users to address.
  • PCI is being treated as an enterprise baseline or “insurance policy,” even for businesses that do not take cards today.
  • WK wants the most optimized solution, not necessarily STA, WEM, or CX3.
  • If STA is ultimately required, WK wants the cheapest way of obtaining it.
  • Cost predictability is important. Leadership strongly dislikes variable overages.
  • AI tokens are attractive because they are fungible across AI capabilities, but WK is concerned about governance, chargeback and unpredictable consumption.
  • WK asked Genesys to model tokens vs WEM vs CX3, not simply recommend the WEM SKU.
  • Corey is specifically looking for validation that the proposed compliance architecture is technically correct.

There is also a terminology issue worth resolving with Corey. The discussion occasionally says PII, but Manjeet consistently frames the immediate requirement as PCI. Those are materially different requirements.

Action item 1

Corey discussion — PCI/PII compliance

The key thing to validate with Corey

“Is WK's mandatory requirement PCI DSS protection of cardholder data, or is there a separate requirement to automatically redact broader PII from every recorded interaction?”

That answer changes the architecture.

If the requirement is PCI DSS

My recommended order of preference is:

1. Secure Call Flow — preferred architectural control for payments

Secure flows prevent the sensitive payment portion from being recorded and prevent the agent from seeing/hearing sensitive data. Genesys specifically describes them as a PCI-compliant approach for payment collection.

Source: Genesys Cloud — Secure flows

For an agent-assisted payment scenario:

Agent → Secure Flow → customer enters card information → PCI-compliant payment data action → return to same agent

The card data never needs to become part of the recording/transcript in the first place.

2. Secure Pause — lowest-friction option

Secure Pause stops recording while payment information is provided. It is also QSA-validated as PCI DSS Level 1.

Source: Genesys Cloud Resource Center — Secure Pause

This option became materially more attractive in 2026. As of March 2, 2026, Genesys expanded Secure Pause to all voice calls, including non-ACD inbound/outbound calls and DID-based callbacks. The release specifically describes the change as closing a compliance gap.

Source: Genesys Cloud announcement — Secure Pause available on all call types

For WK's CX2 agents, therefore, Secure Pause does not require upgrading those users to WEM or purchasing STA just to obtain PCI protection.

The downside is human process: an agent must activate Secure Pause at the appropriate time. For that reason I would favor Secure Call Flow where WK actually processes payments and retain Secure Pause as the fallback.

3. STA sensitive-data masking — defense in depth, not the primary PCI mechanism

STA can automatically identify card number, expiry date, CVV/CID and related sensitive entities and mask them in recordings/transcripts. But Genesys describes this as best effort and explicitly recommends Secure Pause/Secure Call Flow as the first line of defense.

Source: Genesys Cloud Resource Center — sensitive data masking

Most importantly:

Genesys explicitly says Automated Sensitive Data Masking is not PCI DSS compliant by itself.

Source: Genesys Cloud FAQ — Is automated sensitive data masking and redaction PCI DSS compliant?

That point is important for the WK conversation because it challenges the original premise that “we need transcription/STA to get redaction, therefore we need STA to make everybody PCI compliant.”

If WK really needs general PII redaction

Then the conclusion changes.

Automatic PII masking—names, email addresses, phone numbers, locations, national IDs, etc.—is an STA capability. Current documentation says sensitive data masking and the other conversation-intelligence functions require the STA add-on even though basic transcription itself can now be billed separately.

Source: Genesys Cloud — Add Speech and Text Analytics upgrade add-on

So I would make PCI versus PII the first subject in the Corey discussion.

Action item 2

Cheapest/most optimized way to obtain STA

If WK determines it genuinely needs STA for all remaining users, standalone STA via AI Experience is currently cheaper than WEM based both on public pricing and WK's negotiated figures.

Genesys currently meters named-user STA at 30 AI Experience tokens per user. The published US token price is $1/token, making the public economics approximately $30/user/month.

Source: Genesys Cloud tokens model

The current public CX2 WEM add-on price is $40/user/month for named users.

Source: Genesys Cloud pricing hub

Those numbers also explain Tom's comment in the meeting about the difference being approximately $51K annually. The calculation works when applied to the roughly 1,069-user WEM gap, rather than all 2,149 users.

Important 2026 licensing change

There has been a meaningful platform change since some of the assumptions in the meeting.

On April 20, 2026, Genesys changed STA/WEM add-on licensing to be permission based and decoupled transcription usage from STA/WEM license billing.

Source: Genesys Cloud release notes — April 20, 2026

Current documentation says:

  • Transcription alone does not automatically trigger an STA/WEM license.
  • Transcription minutes draw against the organization's pooled transcription allocation.
  • STA conversation-intelligence functions such as topic spotting, sentiment, empathy and sensitive data masking still require the STA entitlement.
  • Billing > User > STA Upgrade can explicitly control which users receive STA.
  • WEM takes precedence when a user already has WEM.

Source: Genesys Cloud — Add Speech and Text Analytics upgrade add-on

This actually creates more optimization possibilities than the meeting contemplated.

CX3

Current public pricing is:

  • CX2: $115 named user/month
  • CX3: $155 named user/month

So the published CX2→CX3 uplift is $40, identical to the published CX2 WEM add-on price.

Source: Genesys pricing

Therefore there is no public-list-price reason to move the entire organization to CX3 merely to obtain STA/WEM. WK's negotiated CX3 discount could alter that, so Tom should still produce the requested commercial model.

CX3 does have broader fair-use allocations. For example, current named-user allocations show 110,000 API-on-demand calls for CX2 versus 140,000 for CX3. CX2+WEM does, however, combine its voice transcription allocations such that the transcription economics need to be examined separately rather than assuming CX3 automatically provides a large advantage.

Source: Genesys Cloud fair use policy

Recommended commercial ranking

PCI only: Secure Flow/Secure Pause → no STA purchase merely for PCI.

PCI + enterprise-wide automatic PII/PCI masking: standalone STA for non-WEM users → approximately $52.6K/year cheaper than extending WEM using the transcript's negotiated pricing.

PCI + genuine WFM/WEM adoption: WEM may justify the ~$52.6K premium because WK then receives forecasting/scheduling, workforce management, performance capabilities, etc.

CX3: pursue only if the negotiated enterprise upgrade economics make it comparable/better than maintaining CX2 + mixed WEM/STA, or if the additional CX3 capabilities/fair-use allocations have measurable value.

Action item 3

Tom/Zach — AI token consumption visibility

The concern expressed by Manjeet and Corey was valid: WK doesn't want one business consuming a large token pool without being able to explain the resulting bill or charge it back appropriately.

The current state is better than the discussion suggests, but not equivalent to a hard budget-control system.

Genesys' current usage reporting documentation says the Billable Usage report exposes AI token usage for named users, organized by charge name, entity/user email or device ID, and timestamp. The Resources Usage report provides daily consumption of billable resources including AI-token-based resources.

Source: Genesys Cloud usage reporting

So the statement in the transcript that WK can only see a total and cannot see named-user token usage is no longer completely accurate.

There are limitations:

  • Usage data is essentially next-day, not real-time.
  • Reports can be generated only once every 24 hours.
  • Current public documentation does not establish a configurable per-user token spending cap.
  • The newer Usage Query Service provides much better filtering, including user ID/client/platform and pagination, but Genesys explicitly warns that its data represents general platform activity and must not be treated as billing data.
  • Genesys is also modernizing/deprecating portions of the older Billing & Usage UI/API infrastructure, so any WK chargeback integration should be designed against the replacement billing architecture rather than hard-coding the legacy interface.

Sources: Usage Query Service announcement · Billing and Usage API/UI deprecation announcement

What Tom should specifically ask Zach/Product

  1. Can WK obtain AI token consumption simultaneously by AI capability + user + date + business unit/division?
  2. Which of those dimensions are authoritative for billing/chargeback, rather than operational usage only?
  3. Is there an API equivalent of the named-user AI token information exposed in the Billable Usage report?
  4. Can WK configure budgets, thresholds, notifications or hard caps before AI token overage occurs?
  5. Can a specific capability such as AI Translate, Copilot, Virtual Agent, etc. be permission-restricted independently to prevent unplanned token consumption?
  6. What is the target architecture replacing the Billing & Usage UI/API, and what should WK build against for enterprise chargeback?

That turns the vague "visibility is improving" discussion into a concrete governance requirement.

Recommendation back to WK

I would not recommend that WK approve 1,069 additional WEM or STA licenses yet solely on the basis of PCI compliance.

The first design review with Corey should validate:

PCI requirement → Enable PCI DSS organizational setting → Secure Flow for structured payment collection → Secure Pause as appropriate/fallback → STA masking only if WK wants defense-in-depth and/or broader PII redaction.

Genesys requires customers intending to handle cardholder transactions to have the PCI DSS organization setting enabled, and the customer responsibility matrix should also be included in the design review.

Source: Genesys Cloud Resource Center

If Corey confirms the real requirement is automatic PII/PCI redaction across every interaction, then STA remains relevant and the commercial recommendation becomes standalone STA for the non-WEM population, with WEM offered only where WK sees enough WEM business value to justify the additional ~$52.6K/year.

That is the path I would take into the Corey conversation because it directly answers Manjeet's request: don't start with a SKU; start with the compliance requirement and find the least expensive architecture that satisfies it.
